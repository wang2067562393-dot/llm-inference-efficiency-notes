# ① KV Cache 压缩

## 1. 瓶颈从哪来

Decoder-only 模型生成时，每个 token 都要用到之前全部 token 的 Key/Value 向量。长度为 L、层数为 $l$、KV 头数为 $h_{kv}$、头维度为 d 的上下文，KV Cache 约占：

```
Bytes ≈ 2 (K,V) × 2 (BF16) × l × h_kv × d × L × batch
```

- 它与上下文长度 L **线性增长**，长文档场景轻易超过模型权重本身；
- MHA（多头注意力）→ GQA/MQA（分组/单头 KV）从结构上减小 h_kv，但长上下文仍然贵；
- 经验事实：长上下文里大量历史位置对当前生成贡献很小（局部性 + 注意力稀疏），这给"丢 KV"留下空间。

## 2. 方法谱系（公开方法）

| 路线 | 代表 | 关键直觉 |
|---|---|---|
| 驱逐（eviction） | H2O | 维护"重型历史（Heavy-Hitter）"，保留累计注意力高的位置 |
| 基于观测窗口 | SnapKV | 用生成前几个 token 当观测窗，聚合注意力定位重要 prompt KV |
| 分层/金字塔预算 | PyramidKV | 不同层保留不同数量：中间层需要更多，首尾层更少 |
| 分块选择 | ChunkKV | 以块为单位做选择，兼顾位置粒度与稳定性 |
| Token 合并 | 通用思路 | 不直接丢，把相近 KV 合并，减少条目数 |

## 3. SnapKV 的算法骨架（必须能手写）

1. 把最后若干个生成 token 作为 **observation window**；
2. 收集每个 prompt 位置从观测窗收到的注意力分数（按头聚合）；
3. 按分数选 top-k% 的 prompt KV 保留，其余丢弃；
4. 之后的 decode 只在保留集上做注意力。

**为什么可能有效**：观测窗把"未来真正会用到哪些历史"这件事显式采样了出来，比单纯按位置或预设置信度更贴近当前请求。

## 4. 代价与评测要点

- 典型失效场景：**大海捞针（needle-in-haystack）**、多事实精确问答、长链推理——被丢的恰好可能是答案位置；
- 评测不能只看困惑度，必须有"长文档精确答案"类指标 + **保留率预算**（如 ≤10% KV）；
- 正确的对照：同模型、同 seed、同保留率预算下 Baseline（如 SnapKV）与候选方法配对跑；
- 注意"每层保留数 + 圆整余量"这种工程细节必须在协议里冻结，否则不同方法不公平。
