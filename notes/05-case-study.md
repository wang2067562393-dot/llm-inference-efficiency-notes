# ⑤ 端到端案例：一次「方法更好」的完整判定

> **本案例的数据全部是合成的**，但每一步都由本仓库的代码真实执行。
> 目的不是宣称某个方法的性能，而是完整演示一件事：**怎么判断一个「提升」是不是真的。**
> 所有命令都能在仓库根目录直接跑。

---

## 0. 场景设定

假设我们在评测一个「视觉 token 削减」方法（用公开论文里的类型做背景，具体数字与结论都是合成的）：

| 项目 | 设定 |
|---|---|
| 可改面 | 只有一个选择函数：输入视觉特征，输出保留的 token 与索引 |
| 冻结 | 模型权重、图像处理、prompt、解码策略、评测脚本 |
| 主指标 | `ms_per_token`（越低越好） |
| 质量门 | 质量 `Q ≥ 0.95·Q_B`，且每个子类 `≥ 0.90·Q_B` |
| 正式 seed | 17 / 43 / 79 |

为什么要先写这张表：**评测的公平性在跑之前就决定了**。跑完再定义指标，等于给自己留后门。

---

## 1. Baseline 选得对不对，比 Reference 强不强更重要

- **Baseline**：保留全部 576 个 patch，不做任何削减。
- 判断它是否「健康」的三条证据：
  1. 它保留了方法必需的输入（没有偷偷关掉某个模块）；
  2. 训练/推理预算与 Reference 相同；
  3. 有公开实现或同协议的健康对照支撑。

> 最常见的作弊不是「Reference 太强」，而是「Baseline 被做弱」：少训几轮、关掉关键模块、换小一点的输入。
> 这样的差距再漂亮也没有意义。

**Reference** 只用来证明「这个任务存在有效改进」，它不是上锚点，也不是标准答案。

---

## 2. 冻结协议：先写死，再开跑

- Baseline / Reference 使用**同一组 seed、同一份数据、同一预算**，一一配对；
- 公开 Dev 用于选方法，**私有 Test 只在最后验收一次**，结果不回灌；
- 主指标、质量门、验收区间、上锚点 **全部事先声明**；
- 正式结果不允许事后挑 seed、挑指标、调锚点。

---

## 3. 三个 seed 的成对结果（合成）

| seed | Baseline (ms/token) | Reference (ms/token) | 改善 |
|---|---|---|---|
| 17 | 12.4 | 8.9 | 3.5 |
| 43 | 12.1 | 8.7 | 3.4 |
| 79 | 12.7 | 9.1 | 3.6 |

命令行算一遍（这就是 `evalkit` 存在的意义——不靠手算）：

```bash
python -m evalkit stats --baseline 12.4 12.1 12.7 \
                        --reference 8.9 8.7 9.1 \
                        --direction minimize --upper 0 \
                        --accept-range 0.15 0.8
```

```
方向            minimize   seed 数 n=3
Baseline 均值   12.400000   样本标准差 σ_B=0.300000
Reference 均值  8.900000   样本标准差 0.200000
改善量 Δ        +3.500000
Δ/σ_B           11.67   （门槛 3）  通过
归一化评分      0.2823   （上锚点 U=0.0）  区间内
```

## 4. 判定

| 检查项 | 结果 | 结论 |
|---|---|---|
| 幅度门槛 | Δ/σ_B = 11.67 ≥ 3 | 过 |
| 归一化评分 | 0.2823 ∈ [0.15, 0.8] | 在验收带内（完成了约 28% 的改进空间） |
| 质量门 | `Q ≥ 0.95·Q_B` 且逐类 ≥ 0.90 | 需要在原始结果里逐项核对 |
| 样本量 | n = 3 | **只能算「强信号」，不能当作统计证明** |

最后一行是很多人忽略的：3σ 是**验收口径**，不是假设检验。n=3 时它连正态性都谈不上，
说「有 99.7% 概率方法有效」是错的。

---

## 5. 四个「看起来通过」的假提升

这一节比上一节重要。下面四种情况，数字都很漂亮，但都不算数。

### A · 单位混用：Δ/σ 算出 6439 倍「改善」

```bash
python -m evalkit stats --baseline 0.62 0.61 0.60 --reference 66 65 64 --upper 100
```

```
Δ/σ_B           6439.00   （门槛 3）  通过
⚠ 疑似小数与百分数混用：标准差与改善量必须统一单位
```

程序会说「通过」，因为它只看到数字。人必须看出 0.62 和 66 不是同一把尺子。

### B · σ = 0：把同一份 checkpoint 当三个 seed

```bash
python -m evalkit stats --baseline 12.4 12.4 12.4 --reference 8.9 8.7 9.1 --direction minimize --upper 0
```

```
Δ/σ_B           —   （门槛 3）  未通过
⚠ Baseline 标准差为 0：改善倍数无定义，需核对 seed 是否真的独立
```

`evalkit` 返回 `None` 而不是 `inf`。所有 seed 结果完全相同，通常意味着 seed 没真正独立
（复制了 checkpoint、评测有缓存），这是危险信号，不是好消息。

### C · 事后把上锚点设成 Reference 的成绩

```bash
python -m evalkit stats --baseline 12.4 12.1 12.7 --reference 8.9 8.7 9.1 \
                        --direction minimize --upper 8.9 --accept-range 0.15 0.8
```

```
归一化评分      1.0000   （上锚点 U=8.9）  超出区间
⚠ 归一化分数 1.0000 超出预声明区间 (0.15, 0.8)：优先复核锚点，而不是改结论
```

分数恒等于 1，因为分母就是「Baseline 到 Reference」本身。**上锚点必须在跑之前用独立依据定死。**

### D · 只有两个 seed 就下结论

```bash
python -m evalkit stats --baseline 12.4 12.1 --reference 8.9 8.7 --direction minimize --upper 0
```

```
Δ/σ_B           16.26   （门槛 3）  通过
⚠ 样本量 n<3：3σ 只能作为启发式，不能当作统计证明
```

数字比三个 seed 时还漂亮——但那是样本量小导致的，不是方法更强。

## 6. 证据链：结论必须能追溯到原始文件

每次正式 run 至少保留：

| 文件 | 作用 |
|---|---|
| `result.json` | 方法、seed、协议、指标、质量门、执行信息 |
| `run.log` | 原始训练与评测输出，供复核 |
| checkpoint + 哈希 | 证明这份结果对应这份权重 |
| 重载校验 | 独立加载后指标一致，排除「只存在于内存里」的结果 |

**缺失字段写 `null` 并说明原因，不许反推或补造。** 一条诚实写 `null` 的记录，比一条编出来的时间戳可信得多。

## 7. 质检：三类致命错误，用工具抓

```bash
python -m evalkit lint tests/fixtures/leaky_task
```

```
严重度 规则 位置                           说明
high   R005 tests/                         tests/ 下没有入口脚本
high   R006 environment/gold_answers.jsonl 选手可见目录里出现疑似答案文件
high   R007 solution/method.py             与 environment/method.py 内容完全相同
```

| 规则 | 现实后果 |
|---|---|
| R006 答案泄漏 | 任务失去区分度，所有候选都能拿满分，返修成本极高 |
| R007 oracle 泄漏 | Reference 实现被复制进选手工作区，等于直接给答案 |
| R005 没有入口 | Verifier 无从执行，整个包无法验收 |

这三类错误都**不会被运行时的报错发现**，只能靠发布前静态检查。

---

## 8. 这套流程能迁移到哪

这套东西和「视觉 token」没有关系，它是**任何「A 比 B 好」的宣称**的通用骨架：

- 模型/推理优化：延迟、吞吐、显存；
- 数据与标注质量：通过率、一致性、异常率；
- 系统与链路：p95 延迟、丢包、降级；
- 甚至简历上的项目：你怎么证明自己做的事有效？

我把它抽成了 `evalkit`。写这个不是为了多一个工具，而是因为**规则写在文档里会被人情绕过，写成会抛错的代码就不会**。
