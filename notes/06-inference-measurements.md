# 06 · 在 12 GB A 卡上实测 Vulkan 推理：从「论文说」到「我测的」

前五篇笔记里的性能数字都来自原论文。这一篇是**自己测的**，回答一个很实际的问题：

> 一张 2021 年的消费级 A 卡（RDNA2、12 GB），跑 7B Q4 到底能有多快？和 CPU 差多少？

## 为什么要测这个

评测工作里最容易被问倒的一句是：「这个提速是真的吗？」
如果从没自己做过测量，就只能复述论文给的百分比。而测量本身有一堆会被忽略的细节：
预热、后端是否真的生效、量化的实际字节数、带宽利用率、以及在什么条件下结论不成立。

这一篇的目标不是刷新纪录，而是**把口径写清楚，让数字能被别人复现**。

## 硬件与软件

| 项 | 值 |
|---|---|
| GPU | AMD Radeon RX 6750 GRE 12GB（RDNA2，`gfx1031`），Vulkan 1.4.315，AMD 专有驱动 26.10.2 |
| 标称显存带宽 | 约 432 GB/s（192-bit GDDR6） |
| CPU | AMD Ryzen 5 5600（6C/12T） |
| 内存 | 16 GB |
| 系统 | Windows 11 Pro 10.0.26300 |
| 后端 | llama.cpp `b12602`（commit `418fe97b5`），Windows Vulkan x64 预编译包 |
| 模型 | Qwen2.5-1.5B-Instruct Q4_K_M（1.12 GB）、Qwen2.5-7B-Instruct Q4_K_M（4.68 GB，两分片） |

## 方法

```bash
# GPU：全部层卸载
llama-bench.exe -m <model.gguf> -ngl 99 -p 512 -n 128 -r 5 -o json
# CPU 对照：不卸载
llama-bench.exe -m <model.gguf> -ngl 0  -p 512 -n 128 -r 5 -o json
```

口径与纪律：

- **pp512** = 预填充 512 token 的吞吐（prompt processing，计算受限）；
- **tg128** = 生成 128 token 的吞吐（text generation，**显存带宽受限**）；
- `-r 5`：同一进程内重复 5 次，输出 `avg_ts` 与 `stddev_ts`；
- **正式测量前先跑一次丢弃**：Vulkan 首次运行要编译 shader 管线，不能算进测量；
- CPU 与 GPU 用同一模型文件、同一 `n_batch`，只改 `-ngl`；
- GPU 是否真的生效，用三条独立证据交叉确认（见下节），不只看速度。

## 结果

| 模型 | 后端 | pp512 (t/s) | tg128 (t/s) | pp 加速比 | tg 加速比 |
|---|---|---|---|---|---|
| Qwen2.5-1.5B Q4_K_M | Vulkan `-ngl 99` | 3063.89 ± 13.00 | **197.13 ± 1.83** | 1.95× | **5.61×** |
| Qwen2.5-1.5B Q4_K_M | CPU `-ngl 0` | 1570.17 ± 66.27 | 35.17 ± 0.86 | — | — |
| Qwen2.5-7B Q4_K_M | Vulkan `-ngl 99` | 789.99 ± 0.66 | **67.20 ± 0.14** | 1.70× | **8.08×** |
| Qwen2.5-7B Q4_K_M | CPU `-ngl 0` | 464.03 ± 8.29 | 8.32 ± 0.13 | — | — |

独立复测（另一进程、`-r 3`）：7B GPU `tg128 = 68.06 ± 0.09 t/s`、`pp512 = 795.77 t/s`。
与上表差 1.3% —— **同机重复也有跨进程方差，报数字要带这个量级**。

### GPU 真的生效了吗（三条证据）

1. `llama-bench --list-devices` 枚举到 `Vulkan0: AMD Radeon RX 6750 GRE 12GB`；
2. 输出 JSON 中 `n_gpu_layers=99`、`backends=Vulkan`、`gpu_info` 为该卡；
3. 显存专用占用从空闲 **1833 MiB** 涨到运行中 **6401–6420 MiB**，增量约 4.5 GiB，与 7B Q4 权重 + KV 相符；
   同时 7B 的 tg 是 CPU 的 8.08×，「实际跑在 CPU 上」可以排除。

## 分析

### 1. 生成速度受显存带宽限制，实测达到标称的约 72%

每生成 1 个 token 都要把全部权重读一遍，所以理论下界是：

```
tg_max ≈ 显存带宽 / 模型字节数
```

- 7B Q4（4.68 GB）：67.2 × 4.68 ≈ **314 GB/s** 有效带宽，约为标称 432 GB/s 的 **72.7%**；
- 1.5B Q4（1.12 GB）：197.1 × 1.12 ≈ **220 GB/s**，只有约 **51%**。

小模型效率更低是预期的：每 token 的固定开销（kernel 启动、采样、注意力）不会随模型一起缩小，
模型越小，这部分占比越高。**这也解释了为什么小模型上 GPU 的加速比反而更低。**

### 2. 为什么 7B 的 tg 加速比（8.08×）远高于 1.5B（5.61×）

CPU 侧：1.5B 还能跑到 35 t/s，7B 掉到 8.3 t/s —— 权重越大，CPU 越被内存带宽掐住。
GPU 侧：12 GB 显存把 7B 完整装下，带宽优势直接兑现。
**模型越大，A 卡相对 CPU 的优势越明显**，这与「大模型才需要 GPU」的直觉一致。

### 3. 预填充是计算受限，加速比明显低于生成

pp512 的加速比只有 1.70× / 1.95×，因为预填充是矩阵乘密集型，CPU 的 AVX2 路径还能撑住，
而 RDNA2 没有矩阵核心（`matrix cores: none`）、Vulkan 后端也未启用 flash-attn。
**推论：这个配置适合「一次给长 prompt、生成较长回答」的场景，不适合高频短 prompt。**

## 局限（这些条件不成立时，上面的数字不成立）

- **单卡、单量化**：只测了 Q4_K_M；Q8 与 F16 会因带宽压力更大而改变加速比；
- **上下文很短**：`-n 128`，没有测长上下文下的 KV Cache 增长对速度的影响；
- **Windows + Vulkan**：Linux + ROCm 通常更快，但没有对比数据；
- **CPU 基线偏保守**：该构建用的是 `ggml-cpu-haswell.dll`，没有 Zen3 专用 DLL，CPU 侧可能略低于最优；
  这会让**加速比偏乐观**，但 GPU 的绝对吞吐不受影响；
- **没有跨机器复现**：只在这一台机器上跑过，未验证换机器后的分布；
- `stddev` 是同一进程内 5 次重复的标准差，**不包含跨进程/跨机方差**（复测显示约 1.3%）。

## 一句话结论

**12 GB 的 A 卡跑 7B Q4 是「可用」级别（67 t/s，约 15 token/秒的 4.5 倍于真人阅读速度），
是 CPU 的 8 倍；但预填充只快 1.7 倍，长 prompt 场景的收益远小于生成场景。**
