# ④ 实验与评测方法论：怎么知道一个提升是真的

> 做算法优化最容易骗的人是自己。这份清单记录我在学习与复现中要求自己遵守的评测纪律。

## 1. 配对多 seed 对照

- Baseline 与 Reference 使用**同一组 seed、同一份数据、同一预算**，一一配对；
- seed 的含义必须写清：是训练初始化、数据顺序，还是（在推理型任务里）请求顺序/配对先后——它们不是一回事；
- **重复评测同一个已生成产物 ≠ 独立重复实验**。确定性重跑方差为 0，不提供任何关于泛化或稳定性的证据；
- 样本量要诚实声明：3 个 seed 只能给出"强/弱信号"，不能宣称严格统计证明。

## 2. 3σ 启发式准则（项目型口径，不是假设检验）

对"越高越好"的指标：

```
Δ   = mean(R) − mean(B)
σ_B = 样本标准差(B, ddof=1)        # 注意分母 n−1
通过门槛：Δ ≥ 3σ_B
```

- 3σ/5σ 是任务验收的**经验规则**，不能说成"有 99.7% 概率方法有效"——这里没有正态总体抽样检验的前提；
- 改善倍数 k = Δ/σ_B 与归一化分要分别报告；
- σ_B = 0 时倍数无定义，需改用真实正向改善 + 归一化范围 + 其他质量条件共同判断。

## 3. 归一化评分锚点

```
越高越好：score = (x − B) / (U − B)
越低越好：score = (B − x) / (B − U)
```

- B 是冻结的 Baseline 锚点（0 分），U 是**事先独立确定**的上锚点（1 分）；
- 对延迟类指标 U 可取理论极限 0 ms/token；对准确率可取 100%；
- **Reference 不是上锚点**，不能跑完后把 U 调成 Reference；也不能为了让分数落进验收区间事后改 B/U；
- 常见验收带（如 0.15–0.8）的含义：Reference 至少要有可见改善，又要给后续优化留足空间。

## 4. 质量门与主分分离

加速/压缩类任务永远是「门 + 连续分」两层：

1. 先过质量硬门（答案差异率、每类指标下限、无效输出率、资源上限、完成度）；
2. 门内才比较速度/成本连续分；
3. 门外用明确的 reward=0 / -10 与具体违规原因处理，**不让候选自报的质量或计时算数**。

## 5. Public/Dev 与 Private 隔离

- 公开集用于迭代和选 best；私有集只在冻结选法后验收一次；
- 私有结果**不得回灌**去继续改方法（no retuning on private feedback）；
- 候选、数据、评分器全部用 **SHA-256 指纹绑定版本**：换任务版本不能继承旧成绩；
- 选型锁版要留下字段证据：`selected_by_public_only`、`no_quality_retry_or_method_change`。

## 6. 时间与资源的诚实记账

- 有效研究时长只算"有证据的分析/实现/训练/评价"，排队、装环境、等 API、空转不算；
- 共享设备（如同一 MIG 上两槽并发）导致的资源竞争必须标注，不能把受污染的小波动当干净复验；
- 缺失的命令、时间、退出码写 null 并解释，**禁止反推或补造**。

## 7. Reward hacking 检查清单（评审 agent 或自己时都用得上）

- 改评分器 / 改数据 / 硬编码答案 / 按结果删题？
- 复用本应独立重训的 checkpoint 冒充新 seed？
- 伪造时间戳、日志或自报分数？
- 利用文件/网络/私有属性访问绕过受限接口？
- 用无意义重复训练凑时长？
- 短测结果冒充完整集成绩？

## 8. 一个必须记住的真实教训

> 在 512 题公开集上 +0.4pp 质量、−18.5% 成本、两次重跑零波动、顺利锁版的策略，
> 在另一个 512 题私有集上质量掉 9.6pp，直接 reward=0。

教训：确定性重跑的零方差 ≠ 稳定；Dev 上的漂亮曲线可能只是过拟合公开集；**多样的公开分层 + 一次性私有验收 + 禁止私有反馈回灌**是唯一可靠的防线。
